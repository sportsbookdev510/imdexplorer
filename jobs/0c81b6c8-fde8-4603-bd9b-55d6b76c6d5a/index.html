    I added invariant tests and edge-case tests for the Conditionals (COND) token, and found no defects. forge build succeeds, and forge test with the verifier's fuzz seed passes all 47 tests: the 33 that were already there, 13 new edge-case tests and 1 invariant suite. Nothing is committed yet.

    The contract: src/ConditionalsToken.sol is the unchanged OpenZeppelin v5 ERC-20. It mints 1,000,000,000 × 10¹⁸ to the deployer once, in the constructor, and has no owner, mint, pause, blocklist, tax or upgrade path. Because nothing failed, I did not write .imd-findings.json.

    Invariant tests (test/ConditionalsToken.invariant.t.sol):

    • Setup: a handler drives the token with six accounts, one of which is the token contract itself. It keeps its own record of what every balance and allowance should be after each call.
    • Normal calls it makes: transfer, transfer of a whole balance, approve (including the maximum value), transferFrom, and a send followed by sending the same amount back. After each one it checks the exact amounts that moved.
    • Failing calls it makes: sending more than the balance, sending to address zero, approving address zero, pulling more than the allowance, and pulling more than the balance. Each must revert with the exact expected error.
    • What must hold after every sequence:
      • the supply never changes;
      • balances add up to the supply;
      • balances and allowances match the handler's record;
      • no failing call ever had an unexpected outcome;
      • nothing ends up at address zero, the handler or the test contract, and the token never holds ETH;
      • name, symbol and decimals stay the same.
    • Settings: 256 runs at depth 64, set in the test file. The tests are also set to fail on any handler revert, so a broken check inside the handler can't be silently skipped. The seeded run made 16,384 calls with 0 reverts.
    • Check on the harness: I ran a copy with a deliberately wrong record and the invariants failed. So the checks really do catch errors.

    Edge-case tests (test/ConditionalsToken.edges.t.sol):

    • An owner needs an allowance even to transferFrom their own account.
    • A zero-amount transferFrom needs no allowance.
    • Pulling from address zero reverts.
    • Spending an allowance emits only the Transfer event, not an Approval.
    • The whole supply can move through a maximum allowance, which is never reduced; an allowance one below the maximum is reduced normally.
    • Approving zero takes the allowance away.
    • A failed pull leaves the allowance and balances unchanged.
    • Tokens sent to the token contract are kept there, not burned.
    • Sending to yourself more than you hold reverts, and so does sending the maximum possible amount.
    • Two fuzz tests, 1,000 runs each: approve always sets the exact value, and sending tokens and back restores both balances.
