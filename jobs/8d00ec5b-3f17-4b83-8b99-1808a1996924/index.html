    The ConditionalsIMD (COND) token is built, and forge build, forge test and forge fmt --check all pass. I ran the tests with the verifier's fuzz seed, both in the repo and in a clean copy of the staged files that only had the vendored libraries. All 19 tests pass.

    What it is (src/ConditionalsIMD.sol)

    • The Solidity contract is named ConditionalsIMD. name() returns "ConditionalsIMD", symbol() returns "COND", and decimals is 18.
    • The constructor takes no arguments and mints the full 1,000,000,000 × 10^18 to whoever deploys it, once. On the launch that is the factory.
    • It is a plain OpenZeppelin v5.4.0 ERC-20. It has no other way to mint, no owner, no pause, blacklist, freeze, burnFrom or upgrade, and no fee or burn on transfer. Every transfer moves exactly the amount asked, so the token doesn't need to exempt the factory, distributor or pool manager.

    Files

    • Config: foundry.toml pins solc 0.8.26 with bytecode_hash = "none", the optimizer on and no ffi or file access.
    • Libraries: forge-std v1.11.0 and OpenZeppelin v5.4.0 are vendored as plain files in lib/, not as submodules.
    • Tests: test/ConditionalsIMD.t.sol checks:
      • the name, symbol, decimals and supply;
      • that the deployer gets the whole supply, including when a factory deploys with CREATE2;
      • exact transfers and allowances;
      • failures: low balance, low allowance, sending to the zero address, approving the zero address;
      • that none of the usual mint or admin calls exist;
      • an opcode scan for DELEGATECALL, CALLCODE and SELFDESTRUCT;
      • two fuzz tests that check the supply never changes and allowances are spent exactly.
    • Script: script/DeployConditionalsIMD.s.sol is a deploy script for local or test networks only. Its deploy() function is tested directly.
    • README: it covers the deployment settings (no constructor arguments, the exact supply, compiler settings, no extra contracts), the assumptions and who is responsible for what. Under "After launch" it says there is nothing to set.

    Things to know

    • Nothing is committed. The files are staged. Git has no author identity on this machine and the brief doesn't ask for a commit, so I didn't set one up. The ignored items are test/scratch/, the build output and a .gitmodules file inside the OpenZeppelin folder that the sandbox wouldn't let me delete. It isn't staged, and there are no submodules.
    • The launch floor tests weren't run here. The provided files depend on harness pieces that aren't in this repo (LaunchLiquidity, PoolInitializationGuard, HookFlags, test/floor/OwnerChecks.sol, v4-core). I covered the same points in my own tests instead: whole supply to the factory, flows that arrive whole, no mint or freeze paths, and the opcode scan. The pool seed and swap haven't been run against a real Uniswap v4 pool manager.
    • No launch.json. I didn't write one, as instructed. That is the manifest step's job.
    • Not run: Slither isn't available here, so it was never run. The token has no custom code beyond the constructor, so none of the six blocking detectors should apply.
