    How the contract works

    • Price: 0.75 units of the approved test ERC-20, sent as 0.50 to the swarm-funding recipient and 0.25 to the treasury. A wallet holding at least one of the configured test identity NFTs pays only the 0.50 to swarm. A "unit" is one whole token, based on the token's decimals.
    • No double payment: each receipt belongs to one wallet and one order ID. Paying the same pair again is refused. Because the wallet is part of the key, nobody can use up another wallet's order ID. Each receipt gets a running number, the amounts, the recipients, whether the discount applied, and a timestamp.
    • Funds: tokens go straight from the payer to the recipients. The contract never holds tokens and refuses ETH. A failed or false-returning transfer cancels the whole payment, so no receipt is left behind.
    • Start-up: the contract starts paused. unpause() refuses until the owner has set the payment token, both recipients (which must be different) and the identity NFT. Each of those setters is owner-only and emits an event.
    • Owner: the launch owner is passed in at deployment as $owner, never the factory or tx.origin. Ownership transfers take two steps (offer, then accept). The constructor makes no calls to other contracts.

    Tests (34): they cover the full and discounted payment splits, a payer losing and regaining the NFT, tokens with different decimals, duplicate and zero order IDs, the wrong or a replaced token, too little allowance or balance, the transfer failures above, a re-entry attempt, the pause rules, the setup checks, owner-only access and ownership transfer. A fuzz test checks that the payer loses exactly what the recipients gain. A deployment rehearsal deploys through a stand-in factory and confirms the owner is the launch owner and the compiled contract contains none of the forbidden instructions.

    What I checked in the price math:

    • Exactness: the price is 10**decimals times 50/100 for the swarm share and times 25/100 for the treasury share. Because setPaymentToken only accepts tokens with 2 to 36 decimals, 10**decimals always divides evenly by 4. Both shares are therefore exact: 0.50 and 0.25 units, and 0.75 in total.
    • Overflow: the largest value is 10**36 * 50, far below the uint256 limit.
    • Decimals: a decimals() value above 255 is rejected before it is narrowed to a uint8. A token that doesn't return decimals is also rejected.
    • Discount: an identity NFT holder pays only the 0.50 swarm share, the treasury transfer is skipped, and the receipt stores address(0) as the treasury recipient.
    • Duplicates: a receipt is keyed by payer and order id, so the same pair can't be paid twice. Payment amounts are recorded before the token transfers, and the nonReentrant guard blocks re-entry.
    • Price changes mid-payment: pay requires the token argument to match the configured token. If the owner switches tokens (and so the decimals), a payment already in flight reverts rather than charging a different amount.
    • Configuration: unpause requires the token, both recipients and the NFT to be set, and no setter can clear any of them back to zero.

    Leads I looked at and didn't report:

    • Fee-on-transfer tokens: the receipt would record more than the recipients actually received. The token is a test token the owner chooses, so this isn't a defect in this release.
    • Shared identity NFT: one NFT passed from wallet to wallet gives each holder the discount in turn. The brief only requires holding the NFT at payment time, so this matches it.
    • Static analysis: the missing zero-address check in transferOwnership is intended, since passing zero cancels a pending transfer and can't make the owner zero. The other lines aderyn reported are style or by-design centralization and don't show a defect.

    Findings (all low)

    1. The identity-NFT setter accepts the payment token (setIdentityNft, line 271). The setter only checks for a non-zero address with code. If the owner sets it to the payment token, every payer counts as an NFT holder, since they must hold the token to pay at all. Every payment then gets the 0.50 price and the treasury gets 0. A scratch test confirmed it: the treasury received 0 instead of 0.25. Fix: reject the payment token's address here, or require the NFT to report itself as ERC-721 (ERC-165).

    2. The recipient setters accept the contract's own address (setSwarmRecipient and setTreasuryRecipient, line 255). If a recipient is set to the contract itself, payments still succeed and receipts are recorded. The tokens then stay in the contract for good because it has no withdraw function. This breaks the "never holds funds" promise in the contract's own comments. A scratch test confirmed 0.5 tokens locked in the contract. Fix: reject address(this) in both setters.

    3. pay() has no maximum-price limit (line 161). The price is worked out when the payment executes, not when the payer saw the quote. Say a payer is quoted 0.50 as an NFT holder and has approved more than that, such as an unlimited approval. If the owner switches the identity NFT before their transaction is mined, they are charged 0.75. A scratch test confirmed it. Fix: add a maxTotal argument to pay and revert when the charge exceeds it.

    Findings 1 and 2 need the owner to make a configuration mistake, which is why they are rated low. Each carries a Foundry proof that fails on the current code and passes once the setter rejects the bad address. Finding 3 has no proof test because fixing it changes the function signature, so it has a written reproduction instead.
